# Audit of the whole platform — 2026-10-19

Scope: repository `omegaswitch/lurdy` on branch `claude/laughing-hypatia-tirtcp` (commit `92c63d1` and the fixes made during the audit), the development Supabase project `LurdyAPP` (eu-west-1), the admin web app, the participant/team app (web build; no physical phone), the Edge Functions, the documentation.

Method: Supabase security and performance advisors; typecheck, builds, lint, Expo Doctor; the SQL suite on a local PostgreSQL 16 with probes written during the audit; four independent code reviews (database and RLS, admin, app, repository) whose findings were each re-verified by reading the code or by a probe against the development project before being accepted; live probes with the publishable key and a staff session (forged `X-Forwarded-For`, `select=*` under column privileges, anon RPC calls). Nothing was tested on iOS or Android devices; everything marked "tested" below ran in the browser or against the database.

**Health score: 78 / 100** (before the audit's fixes: about 55). **Verdict: CONDITIONAL PASS** for the pilot with fictional data; **FAIL for real health data** until the medical module exists and the conditions below are met.

## 1. Findings by severity

Status: **fixed** = changed, re-tested, and (for the database) applied to the development project; **open** = not changed, listed with a recommendation.

### Critical
| # | Finding | Status |
|---|---|---|
| C1 | **Every staff phone downloaded every pilgrim's sign-in code.** The scanner screen loaded `id, first_name, last_name, access_code` of all participants for its manual search, and the `participants_read` policy let any staff member, any carer of a malade, and the medical role read `access_code` with plain REST. The 4-digit code is the pilgrim's only credential: with it one signs in as that person, reads their journey and carers, deletes their account, and obtains a digital badge in their name. | **fixed** — `access_code` is withheld from the API by a column privilege (`revoke select … grant select (…)`), organisers read one code through `participant_access_code`, bulk export through the audited `participant_access_codes`, the scanner searches through `find_participants` (names only). Admin and e2e tests adjusted; `tests/08_hardening.sql` asserts it. |
| C2 | **The sign-in throttle could be turned against others.** A throttled answer was itself counted as a failure for both the address and the code, so one blocked address could lock any code with five requests (and all 10 000 codes in a loop), and a venue NAT with hundreds of pilgrims behind one address locked itself after ten mistypes in 15 minutes. | **fixed** — only wrong guesses count (`reason = 'invalid'`), per-address limit raised to 30, per-code limit stays 5; tested (`08_hardening.sql` §2). |

## 2. Issues verified as not exploitable
- **Forged `X-Forwarded-For`** does not change the throttled address on this project: a request carrying a forged header was logged under the real address. The function now prefers `cf-connecting-ip` and the last hop anyway.
- `participant_card`, `scan_badge`, `issue_credential`, `my_pilgrimage`: membership and role checks are correct; a non-staff caller learns nothing, not even whether a badge exists. The QR carries 122 random bits, only the SHA-256 is stored.
- `anon` has no table privileges in `public`, no usage on `app`, `audit`, `medical`; every public table has RLS; every definer function pins `search_path`.
- A pilgrim sees only their own row; a carer only their malade; assistants are not staff; organiser/medical rights need aal2; an expired or foreign event code removes team rights.
- The `code-login` function keeps the service key server-side; `delete-account` acts only on the bearer's own account.
- No real personal data in seed, fixtures or tests; no secrets in the repository or its history.

## 3. Database and security assessment
Design is sound: RLS on every table, roles derived from grants plus a time-boxed event code, MFA for privileged roles, an audit trigger on every operational table, QR credentials as opaque tokens, health data in a schema no API role can reach. The audit's fixes close the code-exposure, throttle, account-link and lost-phone gaps. What is still missing before real data: (1) the medical module itself (schema `medical` is empty — the "health data never reachable" guarantee currently rests on there being none); (2) a purge job and an approved retention period for `audit.log` and `audit.login_attempts`; (3) the policy rewrite for scale (M15); (4) a decision on the 4-digit code (Q5) — the measured guessing rate is the largest remaining authentication risk; (5) encrypted storage of the session on the phone; (6) a backup/restore drill on a Pro plan.

## 4. UI/UX and accessibility assessment
Both apps follow the Grand Magistry palette, the Asap face and the "big buttons, words not icons" rule; status is always text + icon + colour. Automated WCAG 2.2 AA checks (axe) pass on the tested screens after the contrast and focus fixes; keyboard operation works in the admin (rows are real buttons, timetable buttons carry `aria-pressed`). Not done: a screen-reader session on a real phone, VoiceOver/TalkBack announcements of live regions, and a test with the phone's largest text size. Inconsistent spots: the `en` dictionary is incomplete; three admin screens cannot edit what they create.

## 6. Prioritised recommendations
1. **Before any real data:** decide Q5 (code strength) and Q8 (retention), write the purge job, add `transport_legs (edition_id, code)` unique, run a backup/restore drill, enable leaked-password protection (free).
2. **Before the first stores release:** encrypt the session on the phone (AES key in the keychain, Supabase's documented pattern), switch map tiles to a provider that allows app use, test on real iOS and Android devices, run the screen reader.
3. **Before the medical module:** rewrite the per-row policy helpers for scale (M15), then build `medical.*` with its own access log and break-glass as designed in F §4–5.
4. **Quality:** pending-activation badge state (M16), offline scan queue (M6), the three incomplete admin screens (L12), one language policy (L11), pin React/TypeScript versions (L10).
